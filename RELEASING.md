# Releases

Use squash merges with a Conventional Commit PR title; the squash commit title must match the PR title. CI validates PR titles, tests Python 3.15, builds distributions, checks the wire contract and runs CodeQL. GitHub repository settings must allow Actions to create pull requests. Require CI and PR title checks in branch protection and permit squash merges.

After each push to main, the release workflow examines first-parent commits after `.release-state.json`'s baseline. Only `feat`, `fix` or `perf` commits that change a Python file under `src/pinba/` qualify. Support scopes (`ci`, `tests`, `test`, `docs`, `build`, `release`, `deps`, `dependencies`) never qualify. `feat` increments MINOR; `fix` and `perf` increment PATCH; an eligible breaking marker (`!` or a `BREAKING CHANGE:` footer) increments MAJOR, including before 1.0. Other changes cannot independently trigger a release. Mixed commits qualify when they include runtime Python changes; keep unrelated work in separate PRs. Schema-only, packaging, dependency and workflow changes do not trigger releases by themselves.

When there are eligible changes, automation opens or updates a release PR containing the version, baseline and changelog. Review and squash-merge it after checks pass. Once CI succeeds for the resulting main commit, automation creates a GitHub Release and attaches wheel and sdist. No PyPI publication is configured. Release PRs created by the default GitHub token may not trigger other workflows; use a GitHub App token if required checks do not run, or run and verify checks before merging. If a release already exists the publishing workflow leaves it untouched. Re-run the workflow after transient failures.

The baseline starts at the initial library commit, before the first automated release. Changelog entries list eligible runtime commits; support-only commits remain visible in Git history. The automated release requires GitHub Actions write permissions and repository permission to create pull requests.

## PyPI Trusted Publishing

`publish-pypi.yml` builds the tested release commit and uploads its wheel and sdist to PyPI after CI succeeds. The separate upload job uses the `pypi` GitHub environment and OIDC; no PyPI API token is required. Configure the PyPI trusted publisher for owner `XOlegator`, repository `pinba-python`, workflow `publish-pypi.yml`, and environment `pypi`. The `pypi` GitHub environment must exist and any protection rules must permit the workflow to run. GitHub Release and PyPI publication run independently after successful CI; check both workflows. PyPI releases cannot be overwritten: inspect PyPI before retrying a partially successful upload. A pending publisher does not reserve the project name until the first upload.
